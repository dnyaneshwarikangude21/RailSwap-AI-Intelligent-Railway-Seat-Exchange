# RailSwap AI ML Methodology

## 1. Purpose and scope

This document describes the reproducible machine-learning experiment included in RailSwap AI. The model is an **auxiliary synthetic-compatibility classifier**. It is intended to demonstrate a complete offline data-to-artifact-to-API workflow and to support the academic discussion of recommendation ranking.

The model is **not**:

- a predictor of real passenger acceptance;
- a measure of whether a railway would authorize an exchange;
- a replacement for the deterministic eligibility engine;
- trained from real tickets, PNRs, personal data, or railway records;
- retrained during an API request.

The application's hard eligibility rules remain authoritative. ML output is shown for information and experimentation only.

## 2. Research framing

The experiment addresses three engineering questions:

1. Can a model be trained reproducibly on a pairwise compatibility dataset with grouped splitting?
2. How does the learned classifier compare with a transparent rule baseline on the same synthetic test scenarios?
3. Can inference be integrated safely so that missing or incompatible artifacts degrade to deterministic matching rather than breaking the service?

It does not attempt to estimate a causal effect or real-world recommendation quality.

## 3. Dataset

### 3.1 Generation

File: `backend/ml/generate_dataset.py`

Defaults:

| Setting | Value |
|---|---:|
| Scenario groups | 360 |
| Pairs per group | 12 |
| Random seed | 42 |
| Total rows | 4,320 |
| Output | `backend/ml/data/synthetic_pairs.csv` |

Each group represents a synthetic journey scenario. Twelve pairs are generated within each group so that a group-aware split can prevent near-related rows from appearing in both training and test sets.

Actual target distribution:

| Class | Count | Share |
|---|---:|---:|
| Synthetic compatible (`1`) | 1,590 | 36.81% |
| Synthetic incompatible (`0`) | 2,730 | 63.19% |

### 3.2 Feature generation

Each feature is on a 0-1 scale.

| Feature | Generation / meaning |
|---|---|
| `same_journey` | 1 with probability 0.90 |
| `reciprocal_match` | 1 with probability 0.55 |
| `preference_compatibility` | Uniform 0.72-1.00 when reciprocal; 0.00-0.65 otherwise |
| `coach_compatibility` | 1.0 with probability 0.63; otherwise Uniform 0.30-0.80 |
| `berth_proximity` | Uniform 0.00-1.00 |
| `valid_berth_pair` | 1 with probability 0.97 |
| `journey_active` | 1 with probability 0.95 |
| `scope_satisfied` | 1 with probability 0.95 |

In the live application, the same feature names are computed from actual synthetic pair records:

- reciprocal direction;
- average directional preference satisfaction;
- same-coach bonus;
- normalized berth-distance proximity;
- valid records, upcoming journey, and scope checks.

### 3.3 Label definition

The target `synthetic_compatible` is 1 exactly when:

```text
same_journey == 1
AND reciprocal_match == 1
AND preference_compatibility >= 0.60
AND coach_compatibility >= 0.50
AND valid_berth_pair == 1
AND journey_active == 1
AND scope_satisfied == 1
```

This is a **rule-derived synthetic label**. It intentionally mirrors the documented eligibility policy. There is no observed passenger acceptance in the dataset.

### 3.4 Why the labels matter

Because the label is generated by rules that use the same features, a flexible classifier can learn the rule boundary almost perfectly. That is useful for verifying the data pipeline, feature schema, serialization, and API integration, but it is not evidence that the model generalizes to real passengers.

The project therefore reports classification metrics and Precision@5 while explicitly identifying the circularity.

## 4. Data separation

### 4.1 Ground-truth split

File: `backend/ml/train_model.py`

- Splitter: `GroupShuffleSplit`
- Group key: `group_id`
- Test size: 25%
- Random state: 42
- Train: 3,240 rows across 270 groups
- Test: 1,080 rows across 90 groups

Grouping is important because pairs within a scenario are related. Random row-level splitting would inflate performance by placing near-duplicate scenarios in both partitions.

### 4.2 Leakage controls

- Scenario groups are disjoint between train and test.
- No test labels are used during fitting.
- The imputer and classifier are fitted only on training data inside a pipeline.
- The same deterministic split function is reused by evaluation.

Residual overlap remains by design: the features and target share the same rule semantics. This is a known synthetic-label limitation, not an accidental split leak.

## 5. Model pipeline

```text
Input: 8 features
  -> SimpleImputer(strategy="median")
  -> RandomForestClassifier
       n_estimators = 240
       max_depth = 10
       min_samples_leaf = 3
       class_weight = "balanced"
       random_state = 42
       n_jobs = 1
  -> P(class = 1)
```

Artifact:

`backend/ml/saved_models/railswap_compatibility_rf.joblib`

The artifact is a dictionary containing:

- `pipeline`;
- ordered `feature_names`;
- `schema_version`;
- training metadata.

Metadata:

`backend/ml/saved_models/training_metadata.json`

Evaluation report:

`backend/ml/saved_models/evaluation_metrics.json`

## 6. Evaluation design

### 6.1 Classification

The positive class is synthetic compatibility. At a default threshold of 0.50:

- accuracy;
- precision;
- recall;
- F1;
- confusion matrix;
- per-class classification report.

### 6.2 Rule baseline

The baseline predicts compatible when:

```text
same_journey
AND reciprocal_match
AND preference_compatibility >= 0.60
AND coach_compatibility >= 0.50
AND valid_berth_pair
AND journey_active
AND scope_satisfied
```

For ranking, the baseline uses the live weighted score:

```text
50% reciprocal_match
20% preference_compatibility
15% coach_compatibility
15% berth_proximity
```

These weights are illustrative configuration values and were not optimized on the test set.

### 6.3 Precision@K

Precision@5 is calculated within each test scenario:

1. rank the 12 synthetic pairs by score or predicted probability;
2. take the top five;
3. compute the share that are labeled compatible;
4. average equally across the 90 test scenarios.

It tests ranking usefulness at a small top-K, not operational acceptance. `pair_id` provides a deterministic ascending tie-break.

### 6.4 Latency

After one warm-up call, 300 single-row `predict_proba` calls are timed in a single local process. Reported values include mean, median, and p95. This is not a production throughput benchmark.

## 8. Interpretation

### 8.1 Why perfect classification is expected

The label is a deterministic threshold function of the features. A Random Forest with sufficient capacity can reconstruct that boundary on disjoint but similarly generated scenarios. Perfect test classification validates that:

- feature generation is stable;
- the pipeline learns the intended rule;
- the split does not destroy class structure;
- serialization preserves behavior.

It does **not** validate real-world usefulness.

### 8.2 Why Precision@5 differs

Both classifiers agree on labels, but the ML ranking uses predicted probabilities while the baseline uses the hand-configured weighted score. With only 12 pairs per scenario and a top-5 cutoff, small ordering differences change per-scenario precision. The ML ranking performs better on this synthetic test set, but the result is specific to the generator and weights.

### 8.3 Practical role in the application

The live application uses ML only as an informational confidence:

- eligibility is determined only by hard rules;
- the displayed compatibility score and ranking come from the deterministic baseline;
- an ML failure cannot admit an ineligible candidate;
- the UI labels the confidence as synthetic;
- the ML Lab discloses limitations.

This design avoids allowing an unvalidated model to control consent-sensitive workflow decisions.

## 9. Safe runtime integration

File: `backend/services/ml_service.py`

The service:

1. lazily loads the joblib artifact;
2. verifies pandas/joblib availability;
3. verifies schema version and exact feature order;
4. builds a named-column DataFrame for prediction;
5. returns `P(class=1)` rounded to four decimals;
6. never calls `fit` during a request;
7. caches load attempts and exposes fallback reasons;
8. continues deterministic matching if loading or inference fails.

When an artifact is absent or incompatible:

```json
{
  "available": false,
  "mode": "rule_based_fallback",
  "fallback_reason": "Trained model artifact not found. Using deterministic fallback."
}
```

The API still returns eligible deterministic matches.

## 11. Threats to validity

### Internal validity

- Features overlap with labels by design.
- The synthetic generator may simplify the relationship between preferences and outcomes.
- Hyperparameters were chosen for demonstration, not through extensive search.

### External validity

- No real ticket, passenger, or railway data is used.
- Real acceptance depends on human, operational, policy, fraud, and timing factors absent here.
- The model cannot represent official railway authorization.

### Construct validity

- "Compatibility" is operationalized as a rule-derived label, not measured satisfaction or acceptance.
- Precision@5 measures agreement with synthetic labels.

### Statistical validity

- One grouped split is used.
- No confidence intervals, repeated cross-validation, or significance tests are reported.
- The synthetic dataset is large enough to demonstrate the pipeline, not to support population claims.

## 12. Ethical and privacy considerations

- No real personal data is collected or processed.
- Synthetic names and demo credentials are clearly marked.
- The ML confidence is not framed as a probability of passenger consent.
- Admin views remain redacted.
- The system makes no decision that changes a real reservation.
- The UI repeats that all data is synthetic and the prototype is not affiliated with a railway operator.

## 13. Future work

A genuine study would require:

- ethically approved, consented real-world preference and outcome data;
- a target that measures actual accepted exchanges, not rule agreement;
- temporal and passenger-level leakage controls;
- calibration, fairness, and subgroup analysis;
- repeated grouped cross-validation with uncertainty estimates;
- analysis of false negatives in a consent-sensitive setting;
- human-in-the-loop evaluation;
- privacy-preserving feature design;
- production monitoring, drift detection, and rollback;
- a formal external-authorization integration designed with the railway operator.

Until such evidence exists, deterministic eligibility and transparent scoring should remain authoritative.
